# OpenCode 代码审计：长期记忆构建与版本管理全方案

本文基于 OpenCode 原生能力，结合代码审计全流程闭环，分别从全链路版本管理体系和分层长期记忆构建两大核心维度，提供可落地、可复现、可复用的完整方案。

## OpenCode 代码审计全链路版本管理体系
核心目标：实现审计动作、代码基线、规则迭代、修复闭环全程可追溯、可回滚、可对比，彻底解决审计环境不可复现、过程无记录、结果难追溯的问题。

### 审计前：被审计代码的基线版本锁定

两次被审计的代码之间大概率是没有.git的只有静态代码，要通过选型，静态工具进行diff

### 审计中：审计过程的原子化版本管控

会话级审计过程全归档

OpenCode 原生支持会话管理，每个独立审计任务必须创建专属会话，避免多任务上下文混杂。

核心操作命令：

```
# 查看所有审计会话
opencode session list
# 导出会话全记录（含提问、工具调用、分析过程、中间结论）
opencode session export <session-id> > .opencode/sessions/audit_session_20260507.json
```

导出的会话文件必须纳入 Git 版本管理，实现审计过程全程可追溯，彻底解决 “审计思路断档、历史操作无记录” 的问题。

原子化审计步骤提交

将审计过程拆解为独立原子步骤（架构梳理、漏洞扫描、逻辑审计、边界测试等），每完成一个步骤，将 OpenCode 生成的分析报告、中间笔记、代码片段提交到审计分支。

Commit 规范示例：audit: 完成用户支付模块SQL注入风险审计 | 会话ID:xxx，确保每一步审计动作都有版本记录，可回溯、可拆分、可验证。

修复补丁与审计结果强绑定

针对审计发现的问题，使用 OpenCode 原生 patch 工具生成修复补丁，补丁命名规范：fix/audit-[日期]_[漏洞类型]_[文件路径].patch，同时在补丁注释中关联审计会话 ID、漏洞编号、基线 commit 哈希，确保修复方案与审计结果一一对应，可通过补丁反向追溯完整审计过程。

### 审计规则与环境的版本锁定

自定义规则的 Git 全管控

将 OpenCode 的自定义审计规则（code-review.rules）、权限配置、技能参数，统一存放于项目 .opencode/ 目录下，纳入 Git 仓库管理。每次规则变更（新增漏洞检测规则、调整审计阈值）必须提交 commit，说明变更原因与影响范围，遵循语义化版本号管理规则。

环境兼容性版本锁定

在 .opencode/ 目录下创建 version-lock.json，记录 OpenCode CLI 版本、模型版本、依赖的技能插件版本，避免因工具版本升级导致审计规则失效、审计结果不一致，确保不同环境、不同时间的审计动作可 1:1 复现。

规则迭代的回归验证

每次审计规则更新后，在历史审计基线版本上执行回归审计，对比新旧规则的审计结果差异，将差异报告与规则变更一同提交，确保规则迭代的可验证性，避免规则变更导致的漏报、误报。

### 审计后：结果闭环与归档的版本追溯

审计报告的版本化归档

使用 OpenCode 命令生成结构化审计报告，命令示例：

```
# 批量目录审计，输出json格式报告
opencode skill use code-review --directory src/ --output .opencode/reports/audit_report_v1.2.3_20260507.json
```

同时生成 Markdown 格式可视化报告，一同纳入 Git 管理。每次重审计、补充审计，都生成新版本报告，永久保留历史版本的对比能力。

漏洞全生命周期版本追踪

为每个审计发现的漏洞创建唯一编号（如 AUDIT-20260507-001），通过 Git Issue/PR 关联漏洞编号、审计会话、修复补丁、复测报告。从漏洞发现→修复→复测→闭环，全流程每个节点都有对应版本记录，实现漏洞生命周期全程可追溯。

不可变合规归档

对最终定稿的审计报告、会话记录、基线快照，导出后存入不可变存储（如对象存储 WORM 模式、加密归档），同时生成文件哈希校验值，确保审计归档数据不可篡改，满足等保、合规审计的硬性要求。

## OpenCode 代码审计长期记忆构建方案

核心目标：将单次审计的隐性经验，转化为显性、可复用、可检索的知识资产，解决 OpenCode 跨会话 “失忆”、经验无法沉淀、重复审计成本高的问题，让审计能力持续迭代增强。

### 原生能力最大化：OpenCode 本地持久化记忆配置

核心记忆数据库的备份与管理

OpenCode 默认通过本地 SQLite 数据库存储全量会话、工具调用、上下文信息，默认路径 ~/.local/share/opencode/opencode.db。

制定定期备份策略，执行命令：

```
# 按日期备份核心记忆数据库
cp ~/.local/share/opencode/opencode.db ~/.local/share/opencode/backup/opencode_$(date +%Y%m%d).db
```

对已完成闭环的审计会话，执行 opencode session archive 手动归档，平衡活跃会话的上下文性能与历史会话的完整存储。

项目级全局记忆注入

在项目根目录创建 .opencode/MEMORY.md 项目专属记忆文件，OpenCode 启动时会自动加载该文件，作为全局上下文注入所有审计会话，彻底解决每次新建会话都要重复解释项目背景的问题。

标准 MEMORY.md 需包含以下核心内容：
```markdown
# 项目核心记忆（审计专用）
## 项目基础信息
- 技术栈：Java + SpringBoot + MySQL + Redis
- 架构模式：微服务架构，分为用户中心、支付中心、订单中心3个核心模块
- 审计红线：禁止硬编码敏感信息、禁止未授权访问接口、禁止SQL拼接操作

## 核心业务逻辑
- 支付链路：用户下单→签名校验→额度扣减→订单生成→回调通知
- 权限体系：JWT令牌校验 + RBAC角色权限控制，核心接口需二次鉴权

## 历史重大漏洞与修复方案
- 20260415：订单接口越权访问漏洞，修复方案：添加用户身份与订单归属校验
- 20260420：支付接口SQL注入漏洞，修复方案：替换为预编译SQL语句

## 审计规范与要求
- 高危漏洞必须输出复现步骤与完整修复补丁
- 审计报告必须覆盖机密性、完整性、可用性三个维度
```

分级记忆存储优化

利用 OpenCode 原生三级压缩存储机制，配置分级记忆策略，兼顾性能与完整性：

高频活跃记忆：保留最近 7 天的审计会话完整上下文，用于当前项目的持续审计；

归档记忆：对已闭环的审计会话智能压缩，保留漏洞详情、关键结论、解决方案，剔除冗余对话；

永久记忆：将通用审计规则、项目核心架构、安全红线，写入 MEMORY.md 和自定义技能中，永久生效。

### 核心载体：结构化审计知识资产沉淀

标准化审计知识卡片体系

在 .opencode/memory/ 目录下，按分类创建标准化知识卡片，将单次审计的经验转化为可复用的长期记忆：

```plaintext
.opencode/memory/
├── vulns/          # 漏洞知识库，每个漏洞一个独立文件
│   ├── AUDIT-20260507-001_支付接口SQL注入.md
│   └── AUDIT-20260507-002_用户信息越权访问.md
├── patterns/       # 审计模式库，沉淀特定场景审计方法论
│   ├── 支付接口审计要点清单.md
│   └── JWT认证逻辑通用审计流程.md
├── pitfalls/       # 踩坑记录库，记录误报/漏报场景与解决方案
└── architecture/   # 架构图资产，模块调用关系、数据流转链路图
```

每个知识卡片必须标准化，包含核心信息：编号、类型、风险等级、场景、复现方法、修复方案、关联审计会话、复测结果，确保后续审计可直接复用。

审计经验固化为自定义技能

将沉淀的通用审计规则、检测逻辑、标准化流程，封装为 OpenCode 的自定义 Skill，通过 opencode skill create 命令创建专属审计技能（如 “企业级 Java 代码安全审计技能”“前端 XSS 漏洞自动化检测技能”）。

自定义技能会被 OpenCode 长期存储，支持跨项目、跨会话调用，实现个人 / 团队审计经验的固化和规模化复用。

项目 “逻辑地图” 长期沉淀

针对大型项目，每次审计后，将梳理的模块调用关系、数据流转链路、权限控制节点、外部依赖接口，用 Mermaid/PlantUML 绘制成架构图，存入 .opencode/memory/architecture/ 目录，同时在 MEMORY.md 中建立索引。

让后续审计能快速掌握项目全局，避免重复梳理代码结构，形成项目的长期 “结构记忆”，大幅降低大型项目的审计入门成本。

### 高效复用：跨会话 / 跨项目的记忆检索与共享

可检索记忆索引体系

在 .opencode/memory/ 目录下创建 INDEX.md 索引文件，对所有知识卡片、架构图、审计报告、会话记录，按关键词、漏洞类型、模块、风险等级、时间维度建立结构化索引，支持快速检索。

进阶可配合本地向量数据库（如 Chroma），将所有审计知识向量化，实现自然语言检索，在新的审计会话中，快速召回相关历史经验，彻底解决 “经验找不到、用不上” 的问题。

团队级通用记忆库构建

搭建团队级通用审计记忆仓库，将跨项目的通用安全规则、漏洞修复方案、审计最佳实践、合规要求，沉淀为通用记忆资产。在每个项目的 OpenCode 配置中，通过include指令引入通用记忆库，实现一次沉淀，全团队所有项目复用，避免重复建设。

渐进式记忆迭代机制

采用 “轮次式” 审计方法，每一轮审计都基于上一轮的记忆资产开展，新审计会话开始前，先加载上一轮的审计报告、知识卡片、漏洞清单，让 OpenCode 基于历史结论进行深度审计，而非从零开始。

每轮审计结束后，更新记忆资产，补充新的发现、优化旧的结论，形成记忆的持续迭代和增强，让 OpenCode 越用越 “懂” 你的项目和审计标准。

## 最佳实践与避坑指南

记忆内容边界控制：MEMORY.md 和知识卡片仅记录架构、规则、经验、方案等核心信息，禁止写入 API 密钥、密码等敏感信息，避免记忆文件臃肿导致上下文效率下降。

版本与记忆强绑定：确保每个版本的审计记忆，都与对应的代码版本、OpenCode 版本、规则版本强绑定，避免版本错配导致的审计结果不一致、记忆复用失效。

定期记忆优化清理：每季度对归档会话、历史记忆进行清理，剔除无效、过期内容，合并重复知识，优化记忆文件结构，确保长期记忆的精准性和检索效率。

合规与隐私保护：审计过程中涉及的业务敏感数据、用户信息，禁止写入记忆文件和会话导出内容，备份的数据库文件需加密存储，符合数据安全与合规要求。
